## What is Session Chat and what role it plays interms of Audit and Branching Timeline

It is the central part which allows users to plain the branch and efficiently move between the short term memory and also ai agent getting proper rich history. But also we need to think interms of underlaying system handing the session storage Durability and fault tolerant and Efficiency.

So in this next sections we will move in steps which helped me with incremental improvements to reach the final destination

## Iter 1: What is exactly Does LLM Adapator respond? And how we store it.

In simple terms we recieve a JSON payload which contains a few basic things
- `Role`
- `Content`
- `Usage`
- `Reasoning`

and based on that for each interation with `resp <- provider.Generate()` so then we get `{...}`. which is a individual event and we need to manage the session context over a given Period of Events...

The choice of everyone is `*.jsonl` for storing on your local hardware system.

So I decided to add the meta:
- `last_used_model`
- `session_name`
- `session_uid`
- `working_dir`
- `created_at`
- `updated_at`

and system prompt after that only we added the conversation event. I want you to take note about this as it will be later important.

## Iter 2: Ability to Branch from the main conversation

The first instinct is to create a **Tree** Datastructure for which you are correct. and yes we can represent it even better the classical old linkedlist approach alsoo works but then there is a classical problem. also we cannot use simple tree but a B-Tree as for any given event as a Node we can have N different childreen events as Nodes

**Storage**
with linkedlist approach its possible but not we want to optimize the pointer space as well as It seems unncessary.

**Fetch**
the access pattern should be close to be O(1) as when we do look for a event in the search space.

So at the we wanted array but for any array we have indexes only as O(1) accesspattern and insertion as well which is in this case append only. only problem we need to deal with is Mapping of eventID -> index in the eventID.

once that is decided we can make changes in our events to be

## Iter 3: we need HEAD where we are

Just like what Git does for identifying where it is we are doing to use the HEAD. so that when the session actually moves we can store the eventId and that gives us the latest event of a timeline.
Given, HEAD we can traverse towards the parent which means `id == uuid.Nil` with proper crash recovery.

## Iter 4: then we noticed we can move session meta to seperate file

We saw we have to hack around to just get a sessionmetadata as well as need to load the events.json thus decided to make it a seperate file

which can update last_used_model when the user SwitchModel. and we didn't use the context as Its depend on what user configured as.


```
sessions/<session-id>/
  events.jsonl
  index.jsonl
  session.json
  HEAD
```

and also we made the decision of systemPrompt as its a per agent so better to keep it in the agent loop as a dynamic entity and without adding it in the session becomes true events.
Giving us flexibility later of per model basis system prompt 😉

## Iter 5: HUGE events.jsonl

for that we revisited some of the concepts of logrotate and git how it handles a lot of changes. So got the chunks folder for us to get the benefits of it. so we don't need to open all but a subset of events we just need to open chunks on demand not always.

```
sessions/<session-id>/
  chunks/
    000000.jsonl
    000001.jsonl
  index.jsonl
  session.json
  HEAD
```

We can specify any specific threshold on which we want to rotate and the index file now follows the location to get only a subset of the files to get more efficient read a pos+offset+limit.


and yes we used Digest field to help us out here
